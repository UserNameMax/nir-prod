# Tech Debt

Известные ограничения текущей реализации. Каждый пункт — осознанное решение, принятое для скорости разработки в рамках ВКР.

---

## data-service

### TD-001 — In-memory lock не работает между воркерами Uvicorn
**Ограничение:** `threading.Lock` защищает от конкурентных запросов внутри одного процесса. При запуске Uvicorn с `--workers N > 1` воркеры не шарят память → lock не работает между ними.  
**Сейчас:** запускаем с `--workers 1`.  
**Решение:** файловый lock (`fcntl.flock`) или вынести запись в отдельный write-worker через очередь.

### TD-002 — Offset-пагинация медленная на больших смещениях
**Ограничение:** `OFFSET 500000 LIMIT 1000` в DuckDB сканирует 501K строк.  
**Сейчас:** приемлемо для ВКР, типовые запросы — малые offset.  
**Решение:** курсорная пагинация по `record_id` или `ts_recorded`.

### TD-003 — Нет индексов в parquet
**Ограничение:** каждый запрос по `object_id` + диапазон дат сканирует весь файл.  
**Сейчас:** DuckDB достаточно быстр на 36M строк (~секунды).  
**Решение:** партиционировать parquet по `object_id` или перейти на DuckDB persistent file (`.duckdb`).

## ingestion-service

### TD-004 — Статусы задач теряются при рестарте
**Ограничение:** `dict[job_id, IngestJob]` живёт в RAM. Рестарт контейнера → история пустая.  
**Сейчас:** для ВКР рестарты редки, история не критична.  
**Решение:** SQLite-файл или Redis для хранения статусов.

### TD-005 — Нет retry при сбое записи в data-service
**Ограничение:** если data-service недоступен в момент POST `/sensors/bulk`, батч теряется, задача падает в `error`.  
**Сейчас:** повторная загрузка архива решает проблему (дедупликация по `record_id`).  
**Решение:** retry с exponential backoff (httpx `transport=httpx.AsyncHTTPTransport(retries=3)`).

### TD-006 — Загрузка архива блокирует память
**Ограничение:** весь xlsx-файл читается в pandas DataFrame перед отправкой. Файл 100MB+ → пик памяти ~500MB.  
**Сейчас:** выгрузки ~20-50MB xlsx, приемлемо.  
**Решение:** чанковое чтение `pd.read_excel(..., chunksize=...)` или конвертация в arrow stream.

## ingestion-service

### TD-009 — Прогресс через polling, не SSE
**Ограничение:** viewer запрашивает `/ingest/jobs/{id}` каждые 2с — обновление прогресса с задержкой до 2с, лишние запросы когда ничего не изменилось.  
**Сейчас:** polling простой в реализации, задержка 2с приемлема.  
**Решение:** SSE-эндпоинт `GET /ingest/jobs/{id}/stream` — сервер пушит события по мере продвижения пайплайна.

## viewer

### TD-007 — Нет downsampling для длинных периодов
**Ограничение:** day view загружает до 10K точек (1/мин за день). За неделю — 70K, Recharts начинает тормозить.  
**Сейчас:** просмотр ограничен одним днём.  
**Решение:** LTTB-алгоритм на бэке (параметр `?downsample=N` в `/sensors`).

### TD-008 — Нет кэширования запросов
**Ограничение:** каждая смена дня в DayView → новый запрос к data-service.  
**Сейчас:** запросы быстрые (~100ms), UX приемлем.  
**Решение:** React Query / SWR с кэшированием по ключу `(object_id, date)`.
