# Viewer — Спецификация ML-контура (§10 NARRATIVE)

Расширение существующего viewer'а операционным интерфейсом системы предупреждения
аварий. Базовый data-контур (объекты, календарь, временные ряды, ingest) остаётся как
есть ([viewer/SPEC.md](SPEC.md)); здесь — только ML-поверхность поверх `ml-service`.

## Бизнес-ценность

Рабочее место диспетчера/инженера. Превращает выходы стека §10 в четыре действия:
разобрать **очередь нарядов** на сегодня, спланировать ТО по **watch-list**, изучить
**объект** (риск + срок + профиль), увидеть **честный KPI**. Ключевой принцип UI —
**система это очередь на разбор, а не оракул**: интерфейс не обещает точных
предсказаний, а приоритизирует внимание.

---

## Роль в системе

```
viewer ──REST через nginx──▶ ml-service   (/alerts, /risk, /explain, /kpi)
                          └─▶ data-service (/objects — метаданные)
```

API-клиенты: `mlService.ts` (новый) + существующий `dataService.ts`. Бизнес-логики нет —
только отображение. Триггер/гейтинг/пороги считает ml-service.

---

## Режимы (страницы)

### 1. Очередь нарядов — Слой 2+3 (главный экран)
Ежедневный список объектов к осмотру после триггера, cooldown и (опц.) гейтинга.

- Источник: `GET /alerts/queue?date=&profile=&gate=`.
- Строка наряда: объект (название/муниципалитет), `opened_ts` (начало эпизода),
  острый скор, метка `in_chronic_topK` (в top-K RSF — сильный сигнал), ранг хроники.
- **Селектор профиля триггера** (`ewma10`/`persist5`/`persist7`/`gate_top30`/…) —
  из `GET /alerts/config`; рядом κ*, при каком κ профиль оптимален (κ-envelope).
- **Тумблер гейтинга** Full∧RSF (снижает ложные при дорогих авариях).
- Клик по наряду → drill-down объекта.

### 2. Watch-list — Слой 1
Пообъектный хронический риск (RSF) для планового ТО, вне суточной динамики.

- Источник: `GET /risk/watchlist?top_n=`.
- Подпись: «класс нелинейных моделей» — **не** «чемпион RSF» (CI перекрываются, §5).
- Клик → drill-down объекта.

### 3. Drill-down объекта — Слой 4
Всё про выбранный объект на одном экране.

- **График риска**: дневная история (`/risk/object/{id}`) с пообъектными порогами
  p75/p90 (`/risk/object/{id}/thresholds`); переключение на почасовой
  (`/risk/object/{id}/hourly`). Розовая заливка выше p75 (как в текущем viewer).
- **AFT-срок**: `aft_median_days` из `/explain/{id}` — «ожидаемое время до аварии, дн».
- **Калиброванная вероятность**: `calibrated_prob` — подписана **«для ориентира,
  не порог»** (isotonic — только показ, §9).
- **Суточный профиль**: сырые P/T за день из `/explain/{id}.daily_profile` (регимное
  различие + ночной провал — визуальное подтверждение физики).
- Заголовок: название/тип/муниципалитет/РСО (из `data-service /objects`), ранг риска.

### 4. KPI-панель — отчётность (честный фрейминг)
Источник: `GET /kpi` (только `manifest.reporting`).

- Показывает **temporal**: `detection ≈ 0.48`, `lift +0.20` над случайным полом
  (`detection_null 0.28`), `p<0.001`, `n=92`, `roc 0.775`, `lead_within_H 0.68`.
- **Объект-split 0.70 НЕ показывается** (внутри нулевого пола) — либо скрыт, либо с
  явной плашкой «внутри пола, не операционная цифра».
- Формулировка ценности: «ловит ~половину аварий за месяц вперёд со скромным, но
  статистически реальным преимуществом над случаем». Не «оракул».

## Честный фрейминг (обязательные UI-правила)

Прямо следуют из «чего не делать» (§10 NARRATIVE) — UI не должен вводить в заблуждение:

| Правило | Как в UI |
|---|---|
| Не обещать 0.70 | KPI показывает форкаст 0.48 / lift +0.20; 0.70 скрыт/с плашкой |
| Судить по lift, не абсолюту | detection всегда рядом с `detection_null` и lift |
| Калибровка ≠ порог | `calibrated_prob` подписана «для ориентира»; порог — по рангу |
| RSF — не чемпион | watch-list подписан «класс нелинейных» |
| Система — очередь на разбор | заголовок/подсказки: приоритизация внимания, не автодиспетчеризация |

## Компоненты

| Файл | Назначение |
|---|---|
| `pages/AlertQueue.tsx` | таблица нарядов + селектор профиля (с κ*) + тумблер гейтинга; маршрут `/` |
| `pages/WatchList.tsx` | RSF-ранжирование хроники; маршрут `/watchlist` |
| `pages/ObjectDrilldown.tsx` | плитки (риск/срок/вероятность/хроника) + график риска + суточный профиль; `/risk/:object_id` |
| `pages/KpiPanel.tsx` | temporal detection рядом с полом и lift; `/kpi` |
| `components/RiskChart.tsx` | дневной риск, заливка выше p75, линии p75/p90 и порога алерта |
| `api/mlService.ts` | клиент ml-service (паттерн `dataService.ts`) |
| `types/ml.ts` | типы ответов ml-service |

Data-контур (объекты, календарь, загрузка) не тронут — переехал на `/objects`,
`/calendar`, `/ingest`; главным экраном стала очередь нарядов.

**Порт: 3001** (в `docker-compose.yml` проброс `3001:3000`). 3000 занят демо-стендом
`demo/docker-compose.yml`, который работает параллельно.

**Адрес ml-service** передаётся сборкой через `VITE_ML_API_URL` (по умолчанию
`http://localhost:8005`) — тем же способом, что `VITE_DATA_API_URL`. Прокси nginx не
используется: клиент ходит на сервисы напрямую.

## Потребляемые эндпоинты

| Эндпоинт (ml-service) | Экран |
|---|---|
| `GET /alerts/queue`, `/alerts/config` | Очередь нарядов |
| `GET /risk/watchlist` | Watch-list |
| `GET /risk/object/{id}`, `/hourly`, `/thresholds` | Drill-down (график) |
| `GET /explain/{id}` | Drill-down (AFT-срок, профиль, калибр. вероятность) |
| `GET /kpi` | KPI-панель |
| `GET /objects` (data-service) | заголовки объектов |

## Нефункциональные требования

| Параметр | Требование |
|----------|-----------|
| Внешняя точка входа | порт 3000 (nginx-прокси ко всем сервисам) |
| Отклик | < 2 сек (все данные из кэша ml-service) |
| Бизнес-логика | отсутствует (только отображение) |
| Честность отчётности | temporal/lift, не object-split; калибровка — не порог |

## Текущая реализация (reference)

**Стек:** React 18 + TypeScript + Tailwind + Recharts, nginx (порт 3000) — как
существующий production-viewer. Добавляются: `mlService.ts`, страницы AlertQueue /
WatchList / KPI, расширение drill-down (AFT-срок, профиль). Базовые data/ingest-страницы
не трогаются.

### Ограничения

- Данные статичны между `POST /reload` ml-service (скоры предвычислены из бандла).
- Один регион/сеть; мультитенантность — вне scope v1.
- KPI — валидационные числа из бандла (нет живых меток для пересчёта lift онлайн).
